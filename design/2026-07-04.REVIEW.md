## Phase 1: Prevent Data Loss And False Success

Priority: Critical

Goal: failed or partially failed sends must not be recorded as sent, removed from review, hidden from the badge, or reported as fully successful.

### Finding 1.1: Background Treats Failed Handler Results As Success

Affected files:

- `src/background/background.js`
- `src/handlers/qbittorrent-handler.js`
- `src/handlers/transmission-handler.js`
- `src/handlers/deluge-handler.js`
- `src/handlers/generic-download-handler.js`
- `tests/` new or existing background/handler contract tests

Current behavior:

- `sendTorrentsToHandler()` calls `handler.addTorrents(urls, labels)`.
- Each handler returns an object shaped like:
  - `success`
  - `count`
  - `total`
  - `results`
- Handlers return this object even when some or all individual items failed.
- `sendTorrentsToHandler()` does not inspect `result.success` or `result.results`.
- It records every URL in duplicate tracking.
- It sends `CLEAR_DETECTED_LINKS` to the content script.
- It clears the badge.
- It displays `Successfully processed ${result.count} torrents...`, even when `result.count` is `0` or less than `urls.length`.

Required behavior:

- Treat `handler.addTorrents()` as a structured result, not as success-by-return.
- Only URLs with corresponding `results[]` entries where `success === true` may be added to duplicate tracking.
- Failed URLs must remain available for retry.
- If every URL fails:
  - Do not add any URL to duplicate tracking.
  - Do not clear content-script detected links.
  - Do not clear the badge.
  - Update the badge to the error state for the tab.
  - Return or throw an error response that the caller can display.
  - Notification text must communicate failure, not success.
- If some URLs succeed and some fail:
  - Add only successful URLs to duplicate tracking.
  - Remove only successful URLs from the content script state.
  - Keep failed URLs in the review list.
  - Badge count should reflect remaining failed/not-sent links where practical.
  - Notification text must communicate partial success, for example `Processed 2 of 5 torrents; 3 failed`.
- If all URLs succeed:
  - Existing successful behavior is acceptable.
  - Add all URLs to duplicate tracking.
  - Clear detected links and badge for the tab.
  - Display a success notification.

Implementation instructions:

1. Add a helper in `src/background/background.js` to normalize handler results.
   - Input: original `urls`, optional `labels`, and handler `result`.
   - Output:
     - `successfulUrls`
     - `failedResults`
     - `successCount`
     - `totalCount`
     - `allSucceeded`
     - `allFailed`
     - `partiallySucceeded`
   - The helper must handle malformed handler results defensively:
     - If `result.results` is missing but `result.count === urls.length`, treat all URLs as successful.
     - If `result.results` is missing and `result.count !== urls.length`, treat the operation as failed unless there is a clear success count mapping. Do not guess which individual URLs succeeded.
2. Add a new content-script message type for removing multiple successfully sent links, or reuse repeated `REMOVE_DETECTED_LINK` messages.
   - Preferred implementation: add `REMOVE_DETECTED_LINKS` to `src/utils/constants.js`.
   - Update `tests/constants.test.js` because tests duplicate constants inline.
   - Add a content-script handler that accepts `message.urls` and removes matching links by exact URL.
3. Update `sendTorrentsToHandler()`:
   - Call `duplicateTracker.addHash()` only for `successfulUrls`.
   - Generate and store duplicate hashes for successful URLs with bounded parallelism or `Promise.all`; do not keep the current fully sequential loop when many successful URLs are present.
   - For all-success, send `CLEAR_DETECTED_LINKS`.
   - For partial success, send `REMOVE_DETECTED_LINKS` with successful URLs and do not call `CLEAR_DETECTED_LINKS`.
   - For all-failed, do not remove links.
   - Use `badgeManager.clearBadge()` only when no links remain.
   - Use `badgeManager.updateBadge(tabId, failedCount, true)` for complete failure.
   - For partial success, update the badge to the remaining failed count without the error state unless the intended UX is to display the error state. Use a normal count badge for remaining reviewable items.
4. Update notification text:
   - All success: keep a success message.
   - Partial success: use explicit partial wording.
   - All failed: use explicit failure wording and include the first error message when available.
5. Update return payloads from `sendTorrentsToHandler()`:
   - All success:
     - `{ success: true, count, total, failed: 0, results }`
   - Partial success:
     - `{ success: false, partial: true, count, total, failed, results }`
   - All failed:
     - `{ success: false, count: 0, total, failed: total, results, error }`
   - Do not return `success: true` for partial success.
6. Update popup send behavior if needed.
   - `src/popup/popup.js` currently sends the runtime message and immediately closes the popup without waiting.
   - Minimum required change: background notifications must be correct because the popup will close.
   - Preferred change: only close after the background response resolves for full success. For partial or total failure, keep the popup open and show the error. If implementing this preferred change, update the call to `chrome.runtime.sendMessage()` to `await` the result.

Required tests:

- Add a background send-flow test that stubs a handler returning all failures:
  - Assert no duplicate hashes are recorded.
  - Assert `CLEAR_DETECTED_LINKS` is not sent.
  - Assert error badge update occurs.
  - Assert returned payload has `success: false`.
- Add a background send-flow test that stubs partial success:
  - Assert only successful URLs are hashed.
  - Assert only successful URLs are removed from the content script.
  - Assert `CLEAR_DETECTED_LINKS` is not sent.
  - Assert returned payload has `partial: true` and `success: false`.
- Add a background send-flow test that stubs full success:
  - Assert all successful URLs are hashed.
  - Assert `CLEAR_DETECTED_LINKS` is sent.
  - Assert success payload remains true.
- Add a content-script test for the new `REMOVE_DETECTED_LINKS` message if that message type is introduced.

Acceptance criteria:

- A failed qBittorrent, Transmission, Deluge, or download operation can be retried from the review UI.
- Duplicate tracking contains only successfully submitted or downloaded torrents.
- Notifications and returned message payloads accurately distinguish success, partial success, and failure.
- Existing tests pass.
- New tests fail before the implementation and pass after it.

### Finding 1.2: Popup Renders Untrusted Torrent Data With Attribute Interpolation

Affected files:

- `src/popup/popup.js`
- `tests/` new popup DOM rendering test if a popup test harness is added

Current behavior:

- `createTorrentElement()` builds torrent rows with `innerHTML`.
- Torrent name and URL text are passed through `escapeHtml()`, which is sufficient for text-node insertion.
- The same escaped values are also interpolated into double-quoted attributes, for example `title="${escapeHtml(torrentName)}"`.
- `escapeHtml()` uses a text-node round trip. It does not escape double quotes in text content, so a magnet display name containing `"` can break out of the `title` attribute.
- The untrusted input source is page content: torrent URLs and magnet `dn` values originate from arbitrary websites.

Required behavior:

- Do not interpolate untrusted torrent names, URLs, labels, or element text into HTML attribute strings.
- Build torrent rows with DOM APIs for all untrusted values:
  - Use `document.createElement()`.
  - Use `textContent` for visible text.
  - Use `setAttribute('title', value)` for titles.
  - Use `classList.add()` only with controlled class names from local code.
- Controlled SVG/icon markup may remain static, but it must not contain untrusted interpolated data.

Implementation instructions:

1. Rewrite `createTorrentElement()` in `src/popup/popup.js` to avoid `element.innerHTML` for the row structure that contains untrusted torrent data.
2. Preserve the current visual structure and CSS class names:
   - `.torrent-item`
   - `.torrent-checkbox`
   - `.torrent-info`
   - `.torrent-name`
   - `.torrent-details`
   - `.torrent-type`
   - `.torrent-url`
   - `.torrent-label`
   - `.label-input`
   - `.torrent-actions`
   - `.remove-btn`
3. Create the remove button icon with static markup or DOM APIs. Do not combine static SVG markup with untrusted strings.
4. Keep existing event behavior:
   - Clicking the row toggles selection.
   - Clicking the checkbox only toggles selection once.
   - Clicking the label input does not toggle selection.
   - Clicking remove removes that torrent.
5. After rewriting, delete `escapeHtml()` from `popup.js` if it is no longer used.

Required tests:

- If adding a popup DOM test harness is practical, add a test where the magnet `dn` contains a double quote and an attribute-like payload.
- Assert the generated `.torrent-name` text matches the decoded name.
- Assert the malicious text does not create extra attributes on `.torrent-name` or ancestor elements.
- Assert the remove button and checkbox still work.

Acceptance criteria:

- Popup rendering treats all detected torrent data as text or attribute values set through DOM APIs.
- A crafted magnet display name cannot break row markup or add attributes.
- Existing popup behavior is preserved.

## Phase 2: Fix Configuration Migration And Built-In Pattern Drift

Priority: High

Goal: users who already have saved config must receive corrected built-in pattern and filter definitions when the extension updates, while preserving user-owned custom entries.

### Finding 2.1: Built-In Items Are Only Added, Not Reconciled

Affected files:

- `src/utils/config.js`
- `tests/source-contract.test.js`
- Possibly `tests/content-detection.test.js`

Current behavior:

- `deepMerge(DEFAULT_CONFIG, stored)` preserves stored arrays wholesale when both default and stored values are arrays.
- `ensureBuiltinItems(currentArray, defaultArray)` only pushes missing built-in IDs.
- If a built-in pattern already exists in storage, its `regex`, `name`, or other default-owned fields are not updated.
- This means a user can keep stale built-in definitions forever.
- The project notes specifically call out that `html-torrent-downloads` was previously too broad and must not regress.

Required behavior:

- Built-in items are extension-owned for these fields:
  - `id`
  - `name`
  - `regex`
  - `builtin`
- User-preserved fields for built-ins:
  - `enabled`
- Custom items must be preserved exactly except for validation/migration explicitly required elsewhere.
- Missing built-ins must still be added.
- Existing built-ins must be reconciled to the current default definition while preserving enabled/disabled state.

Implementation instructions:

1. Replace or extend `ensureBuiltinItems()` in `src/utils/config.js`.
2. Use a deterministic merge strategy:
   - Start with the current stored array.
   - For each default built-in item:
     - If stored item with same `id` exists:
       - Replace extension-owned fields from default.
       - Preserve `enabled` from stored if it is a boolean.
       - Force `builtin: true`.
     - If no stored item exists:
       - Add a shallow copy of the default built-in item.
   - Preserve all non-built-in items from storage.
3. Keep array order stable and predictable:
   - Built-ins should appear in the same order as `DEFAULT_CONFIG`.
   - Custom items should follow built-ins in their existing relative order.
4. Ensure this reconciliation is applied to both `patterns` and `filters`.
5. Do not re-add generic URL patterns such as broad `/download/` matches to `html-torrent-downloads`.

Required tests:

- Add a source contract test where storage contains a stale built-in `html-torrent-downloads` regex.
  - Assert `getConfig()` returns the current default regex.
  - Assert the stored `enabled` state is preserved.
- Add a test where a built-in pattern is missing.
  - Assert it is restored.
- Add a test where a custom pattern exists.
  - Assert it remains present and unchanged.
- Add equivalent filter reconciliation coverage or a parameterized helper test that covers both arrays.

Acceptance criteria:

- Existing users receive corrected built-in pattern/filter definitions on config load.
- Users who disabled a built-in item do not have it silently re-enabled.
- Custom user patterns and filters remain intact.
- Existing tests pass.

## Phase 3: Correct URL Identity, Unicode Handling, And Duplicate Semantics

Priority: High

Goal: detect and track torrents by stable torrent identity without crashing on valid web URLs or collapsing distinct query-driven downloads.

### Finding 3.1: Detected-Link Storage Keys Are Not Tab-Scoped And Are Not Cleaned Up

Affected files:

- `src/background/background.js`
- `src/content/content-script.js`
- `src/utils/constants.js`
- `src/utils/hash.js` only if a shared raw-string hash helper is added there
- `tests/constants.test.js` if a message type is added
- `tests/content-detection.test.js`

Current behavior:

- `content-script.js` has a `getTabId()` helper, but it does not return the Chrome tab ID.
- `getTabId()` uses `btoa(window.location.href)` and takes the first 20 sanitized characters as a pseudo-tab identifier.
- `btoa()` throws when the input string contains characters outside Latin-1.
- Many valid URLs can contain Unicode characters in path, query, or hash.
- If `getTabId()` throws, initialization can fail before storage load or scan.
- `getTabId()` strips non-alphanumeric characters and truncates to 20 characters.
- Different URLs with the same early encoded prefix can map to the same key.
- Two tabs with the exact same URL map to the same key and can read each other's stored detected links.
- When SPA navigation changes `window.location.href`, the script clears in-memory `detectedLinks` and computes a new `storageKey`, but it does not remove the old `detectedLinks_*` entry from `chrome.storage.local`.
- Old detected-link storage entries can accumulate indefinitely, including after a tab is closed.

Required behavior:

- The primary storage key must be scoped to the actual Chrome tab ID.
- The fallback storage key must be Unicode-safe and bounded if tab ID resolution fails.
- Two tabs with the same URL must not share detected-link storage when the background can resolve `sender.tab.id`.
- Old `detectedLinks_*` entries must be removed when a tab navigates or closes.
- Clearing detected links must remove or empty the current storage key consistently.

Implementation instructions:

1. Add a content-to-background message type, for example `GET_TAB_ID`, to `src/utils/constants.js`.
   - Update `tests/constants.test.js` because it duplicates constants inline.
2. In `background.js`, handle `MESSAGE_TYPES.GET_TAB_ID`:
   - Respond with `{ tabId: sender.tab?.id ?? null }`.
   - Return synchronously; this message does not need `return true`.
3. Replace content-script `getTabId()` with async storage-scope helpers:
   - `async function getStorageScopeId()`
   - `async function computeUrlFallbackScopeId(url)`
4. `getStorageScopeId()` must:
   - Try `chrome.runtime.sendMessage({ type: MESSAGE_TYPES.GET_TAB_ID })`.
   - If the response has a numeric `tabId`, return `tab_${tabId}`.
   - If the message fails or no tab ID is returned, return `url_${hash}` where `hash` is a SHA-256 hex digest of the full URL string.
5. `computeUrlFallbackScopeId(url)` must:
   - Encode `url` with `TextEncoder`.
   - Hash with `crypto.subtle.digest('SHA-256', encodedUrl)`.
   - Convert the digest to lowercase hex.
   - Not use `btoa()`.
   - Not truncate to 20 characters.
6. Make storage-key initialization explicit:
   - `initializeContentScript()` must await the storage scope before `loadFromStorage()`.
   - `getStorageKey()` should only apply the `detectedLinks_` prefix to the current scope ID.
7. When `scanPage()` detects `window.location.href !== currentUrl`:
   - Store the previous `storageKey` before recomputing.
   - Clear `detectedLinks`.
   - Update `currentUrl`.
   - If the scope is tab-based, keep the same storage key but remove its current stored value so old-page detections do not survive navigation.
   - If the scope is URL-fallback-based, recompute the fallback scope from the new URL and update `storageKey`.
   - Call `chrome.storage.local.remove(previousStorageKey)` if the previous key exists.
   - Ignore storage remove errors caused by extension-context invalidation using the existing invalidation path.
8. In the `CLEAR_DETECTED_LINKS` message handler:
   - Clear `detectedLinks`.
   - Remove the current storage key with `chrome.storage.local.remove(storageKey)` instead of saving an empty array.
   - If preserving the empty-array behavior is required for compatibility, first remove the key and then avoid re-creating it until a non-empty scan result exists.
9. Update `saveToStorage()`:
   - If `detectedLinks.size === 0`, remove `storageKey` instead of storing `[]`.
   - Otherwise store the current link array as before.
10. In `background.js`, add `chrome.tabs.onRemoved` cleanup:
    - Remove `detectedLinks_tab_${tabId}`.
    - Ignore cleanup errors.
11. Do not add `chrome.alarms` for this cleanup.

Required tests:

- Add a content-script test with a page URL containing Unicode characters.
  - Assert initialization completes.
  - Assert detected links are returned normally.
- Add a content-script test with a very long URL.
  - Force the fallback path.
  - Assert storage-key length is bounded to `detectedLinks_url_` plus a SHA-256 hex digest.
- Add a content-script test where the mocked background returns distinct tab IDs for two same-URL instances.
  - Assert the storage keys are `detectedLinks_tab_<id>` and do not collide.
- Add a content-script test that simulates URL change or invokes the scan path after changing `window.location.href`.
  - Assert the previous/current stored detections are removed from mocked storage.
  - Assert the new key is different for two URLs that share the same first 20 characters.
- Add a content-script clear test.
  - Assert `CLEAR_DETECTED_LINKS` removes the current storage key.
- Add a background test for tab removal cleanup if a background test harness is added.
  - Assert closing tab `123` removes `detectedLinks_tab_123`.

Acceptance criteria:

- Content script initializes successfully on pages with Unicode URLs.
- Two tabs with the same URL do not share stored detected links.
- Nearby URLs do not collide in fallback mode because of a 20-character prefix.
- Very long page URLs do not become very long storage keys in fallback mode.
- Old detected-link storage entries created by URL changes or tab closure do not accumulate.
- Existing detection behavior remains unchanged except for the storage cleanup.

### Finding 3.2: Query-Driven Torrent URLs Are Collapsed Incorrectly

Affected files:

- `src/content/content-script.js`
- `src/utils/hash.js`
- `tests/hash.test.js`
- `tests/source-contract.test.js` or new source hash tests
- `tests/content-detection.test.js`

Current behavior:

- `getContentKey(url)` returns `urlObj.origin + urlObj.pathname` for non-magnet URLs.
- `hashUtils.generateHash(url)` lowercases and hashes `url.split('?')[0]`.
- Distinct URLs such as these collapse to the same content key and duplicate hash:
  - `https://example.test/download.php?id=1`
  - `https://example.test/download.php?id=2`
- Many torrent sites serve different torrents from the same endpoint with query parameters.

Required behavior:

- Magnet links should continue to dedupe by BTIH hash.
- Direct `.torrent` URLs with cachebuster-only query parameters may still dedupe if that is an explicit rule, but query-driven endpoint downloads must not collapse.
- The default safe behavior is: include query string in identity for non-magnet URLs.

Implementation instructions:

1. Update `getContentKey(url)` in `src/content/content-script.js`.
   - For magnets: keep current BTIH behavior.
   - For parseable non-magnet URLs: return a normalized URL that includes origin, pathname, and search.
   - Exclude hash fragments unless there is a torrent-specific need to include them.
   - Normalize host casing through the `URL` object.
2. Update `hashUtils.generateHash(url)` in `src/utils/hash.js`.
   - For magnets: keep current BTIH behavior.
   - For non-magnet URLs: hash a normalized string that includes query string.
   - Do not lowercase the entire URL because path/query can be case-sensitive on some servers.
   - Use `new URL(url)` where possible and normalize only protocol and host through URL parsing.
   - For unparsable URLs, hash the original string.
3. Do not introduce site-specific allowlists or blacklist query parameters in this phase.
4. If cachebuster dedupe is desired later, document it as a separate feature with explicit query parameter rules.

Required tests:

- Add source hash tests using actual `src/utils/hash.js`, not only inline doubles:
  - Two URLs with same path and different `id` query values must produce different hashes.
  - A URL with different fragment only should produce the same hash if fragments are intentionally excluded.
  - Magnet URLs with same BTIH and different tracker lists must still produce the same hash.
- Add content detection coverage:
  - A page with two links to the same path and different query IDs must report two links.
  - A page with duplicate magnet links with same BTIH and different trackers must report one link.

Acceptance criteria:

- Query-distinct torrent downloads are not silently dropped during detection.
- Query-distinct torrent downloads are not treated as duplicate sent items.
- Magnet duplicate behavior remains stable.

### Finding 3.3: Scheduled Initial Scans Can Run Before Config Is Loaded

Affected files:

- `src/content/content-script.js`
- `tests/content-detection.test.js`

Current behavior:

- The content script registers a load/ready-state scan timer before `await initializeContentScript()` runs.
- `initializeContentScript()` is responsible for setting `config`.
- If the page is already complete, `setTimeout(scanPage, 1000)` can fire while `configUtils.getConfig()` or storage load is still pending.
- `scanPage()` can then run with `config === undefined`.
- In that case the scan can fail in `detectLinksInChunks()` when reading `config.performance` or `config.patterns`.
- If the premature scan has set `isScanning = true`, the later initialization scan can return early, leaving the page unscanned until a later mutation or visibility event.

Required behavior:

- No scan path may execute until content-script initialization has loaded config and storage state.
- Timers and event listeners may be registered before initialization completes only if their callbacks gate on an initialization promise.
- A failed early scan must not block the real initialization scan.

Implementation instructions:

1. Add an initialization state:
   - `let initializationPromise = null;`
   - `let isInitialized = false;`
2. In `initializeContentScript()`:
   - Set `initializationPromise` before starting async work.
   - Set `isInitialized = true` only after `config`, `storageKey`, storage load, mutation observer setup, and initial scan setup are ready.
3. Add a helper:
   - `async function scanWhenReady() { await initializationPromise; return scanPage(); }`
   - If initialization failed because the extension context was invalidated, return without throwing.
4. Use `scanWhenReady` for:
   - document complete timer
   - window load timer
   - visibility-change delayed scan
   - mutation-observer debounced scan
   - `RESCAN_PAGE` message path
5. Keep `scanPage()` itself defensive:
   - If `!config`, return without setting `isScanning = true`.
   - Do not log a user-visible error for this guard.
6. Ensure `initializeContentScript()` still performs exactly one initial scan after config is ready.

Required tests:

- Add a content-script test where `configUtils.getConfig()` resolves after a delayed promise.
- Simulate the document-complete timer firing before config resolves.
- Assert no uncaught error is logged from `scanPage()`.
- Assert the final detected links are available after initialization resolves.

Acceptance criteria:

- Slow `chrome.storage.local` or slow config loading cannot cause the content script to miss the initial scan.
- Page load, visibility, mutation, and manual rescan paths all wait for initialization.

## Phase 4: Make The Build Script Match The Documented Build System

Priority: Medium

Goal: `npm run build` must leave esbuild output in `dist/` for `background.js`, `popup.js`, and `options.js`, as documented by project instructions.

### Finding 4.1: Copy Pass Overwrites Esbuild Bundles

Affected files:

- `build.js`
- `tests/` optional build behavior test
- Possibly `dist/` only if intentionally regenerated by the implementing agent

Current behavior:

- `build.js` creates esbuild bundles for:
  - `src/background/background.js`
  - `src/popup/popup.js`
  - `src/options/options.js`
- After bundling, `copyDir(srcDir, distDir)` walks `src/`.
- Its copy condition is:
  - copy non-JS files, or
  - copy files where `shouldBundle(entry.name)` is true.
- Since `shouldBundle('background.js')`, `shouldBundle('popup.js')`, and `shouldBundle('options.js')` return true, the raw source files overwrite the bundled files.
- Existing `dist/` entry files confirm plain source output.

Required behavior:

- Bundled entry points must not be overwritten by the copy pass.
- Non-entry JS files that are intentionally loaded separately must continue to be copied:
  - content scripts
  - utility scripts
  - handler scripts
- Non-JS assets must continue to be copied.
- The build must fail if `dist/manifest.json` references a missing script, HTML page, icon, or locale directory.

Implementation instructions:

1. Change copy behavior in `build.js` to skip only the exact bundled entry paths:
   - `background/background.js`
   - `popup/popup.js`
   - `options/options.js`
2. Do not skip all JS files.
   - The manifest content script depends on separate files:
     - `utils/config.js`
     - `utils/hash.js`
     - `utils/constants.js`
     - `content/content-script.js`
   - Options and popup HTML also load helpers and handlers directly.
3. Use relative paths from `srcDir` for the skip check, not just filename, so future files named `background.js` in another directory are not accidentally skipped unless intended.
4. Add a post-build smoke check in `build.js` after copy/bundle work:
   - Parse `dist/manifest.json` with `JSON.parse`.

- `src/options/options.js` only if user-facing validation messages change
- `README.md` only if the ReDoS wording is updated there
- `tests/source-contract.test.js` or new config validation tests

Current behavior:

- `validateRegexPattern()` compiles a user regex and measures one `regex.test()` call against `'a'.repeat(1000)`.
- If execution takes more than 100ms, the regex is rejected.
- This is a useful basic guard, but it does not prove a regex is safe against all catastrophic-backtracking inputs.
- Some comments and docs describe the check as ReDoS protection, which can overstate the guarantee.

Required behavior:

- Keep a lightweight synchronous regex validation guard.
- Describe the guard as a basic execution-time heuristic, not complete ReDoS prevention.
- Test more than one representative input so obvious URL-shaped pathological cases have a better chance of being caught.

Implementation instructions:

1. Update comments in `src/utils/config.js`:
   - Replace wording like `prevent ReDoS` with `reduce obvious ReDoS risk` or `basic execution-time guard`.
2. Update `validateRegexPattern(pattern)`:
   - Compile the regex once.
   - Test against a small corpus, not only `'a'.repeat(1000)`.
   - Include at least:
     - `'a'.repeat(1000)`
     - `'a'.repeat(1000) + '!'`
     - a long URL-like string such as `https://example.test/` plus repeated path segments
     - a long magnet-like string with repeated query parameters
   - Measure each test input.
   - Reject if any single test exceeds 100ms.
   - Reset `regex.lastIndex = 0` before each test.
3. Keep validation synchronous.
4. Do not introduce a Web Worker or async timeout architecture in this phase.
5. Update README wording if it implies complete ReDoS prevention.

Required tests:

  - A syntactically invalid regex fails.
  - A known pathological regex fails if it exceeds the configured threshold in the test environment.
- Avoid timing-flaky tests where possible. If a pathological timing test is too flaky in Jest, test that the corpus is exercised by factoring corpus generation into a helper.

Acceptance criteria:

- Regex validation remains lightweight and synchronous.
- Documentation and comments no longer overstate the guarantee.
